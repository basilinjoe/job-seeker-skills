# gaps.ttl — implementation plan

**Spec:** none. This plan and its Rulings are the spec, as in the graph-rewrite phases.
**Reverses:** the roadmap's `gaps.md (prose, unchanged)` (`2026-09-24-graph-rewrite-roadmap.md:26`).

## Context

`gaps.md` is the one place where the analyst's judgement exists only as a Markdown table.
`jsk match --gaps` reads it back with `match.gaps_table` (`match.py:308`): it splits on `|` under a
heading that must read exactly "Requirements", uses column headers that must match exactly, and
pairs rows to requirements by normalised free text. A reworded row "matches no requirement". A
`|` in a cell splits it. `cites_id` accepts anything shaped like an id, whether or not the id
exists. Nothing downstream can query the verdicts, and nothing can ask across applications which
requirements the person is usually short on.

**Most of gaps.md does not need a model at all.** This was measured on a scratch copy of the real
workspace (24 postings, 407 requirements):

- Loading the workspace takes 488 ms, and `jsk match` takes 46–152 ms per posting (median 99 ms).
  In that time the match already decides each requirement's default verdict, its evidence, the
  reason for its bucket (`near[].why`, the evidence kind), the Ranking, the Cover and most of the
  questions.
- In the three runs made with the current flow (jumpcloud 41 rows, stickermule 11, nagarro 39),
  the analyst **kept the match's verdict on every row but 7**. The 12 nagarro rows that differ
  postdate the run: the career changed after it.
- All 7 lowerings are about meaning the triples do not carry:
  - scope: "mentors *junior*, not senior"; "stakeholders were non-technical, not executives";
    "single-cloud, not multi-cloud";
  - intent: "builds AI for others, not using it";
  - products named in the advert and absent from the evidence: "Pinecone, Weaviate, Milvus";
    "Cursor, Copilot".

So `gaps.ttl` is **derived by code**, in under a second, from posting.ttl, kb.ttl and the
vocabulary. The analyst adds only a small overlay: lowered verdicts with reasons, eligibility, fit,
and the wording of the questions. Code writes the Turtle and renders `gaps.md`, and no code reads
`gaps.md` again.

**No new verb.** The old JSON gaps format (UGS, `.gaps.json`) was removed in `99b9185` because of
its command surface, not because it was structured. This plan changes what `jsk tailor prepare`,
`--gaps` and `--draft-gaps` do, and adds nothing to SKILL.md's command table.

## Rulings

Each ruling says what it costs if it turns out wrong.

1. **Three files, one owner each.**
   - `gaps.ttl` is code's: the match, derived, plus the overlay folded in.
   - `gaps.md` is code's: rendered from `gaps.ttl` and the match. It starts with
     `<!-- written by jsk from gaps.ttl - edit gaps.txt, not this -->`, which deliberately does not
     contain the `<!-- jsk:` slot marker.
   - `gaps.txt` is the analyst's overlay, drafted by code. It is the only file a model edits.

   *If wrong:* one more file per application. The alternative is a gaps.md with mixed ownership,
   which is the fragility being removed.
2. **What is derived.** For each requirement, `gaps.ttl` holds:
   - `j:matched`: the match's verdict (`match.verdict`).
   - `j:verdict`: the verdict that stands, which is `j:matched` unless the overlay lowered it.
   - `j:evidence`: the confirmed carriers when satisfied, the carriers when unevidenced, the
     `near` projects when partial.
   - `j:basis`: a mechanical sentence per bucket:
     - `near`: the `near[].why` text, e.g. "implied by c:x; confirm" or "holds broader c:x";
     - `unevidenced`: "carried by prj_a (tag), prj_b (unconfirmed) only";
     - `missing`: "nothing in the record holds c:x";
     - `ambiguous`: "names several concepts: c:a, c:b";
     - `candidate`: "no concept holds it";
     - `implicit`: the current `IMPLICIT` text.
   - `j:flag`: the review flag of Ruling 3, when it fires.

   The Assessment holds:
   - `fit`: a default from a rule, unless the overlay sets it. `poor` when any `required`
     requirement is `unsatisfied`; `strong` when every `required` one is `satisfied`; otherwise
     `partial`.
   - `eligibility`, `fallsShort`, `surplus` and `questions`, from the overlay. `questions`
     defaults to the match's questions in the order the analyst works through them.

   *If wrong:* the fit rule is one function, and the analyst overrides it anyway.
3. **One review flag, `listed-names`, and one rejected.** Both were prototyped over the corpus.
   - **`listed-names` is kept.** A `satisfied` row whose `asked` lists items, either in
     parentheses or as ≥2 comma-separated items (split on `,`, `/`, ` and `, ` or `), is flagged
     when an item appears, case-insensitively and whole-word, in no confirmed evidence bullet's
     `j:text`. It fired on **7 of 105** satisfied rows across all 24 runs. At least 4 of those 7
     are rows the analyst lowered. In the recent runs it fired only on lowered rows (3 of 3).
   - **`shown-but-not-named` is rejected.** It flagged a satisfied row whose confirmed bullets
     never contain a label of its concept. It fired on **66 of 105**, which is noise.

   A flagged row is not lowered by code. It becomes a slot in `gaps.txt` that the analyst must
   answer with `keep` or a lowered verdict and a reason. *If wrong:* the flag is one function, and
   a noisier or quieter rule swaps in. Tune it against the corpus, never by feel. A known
   weakness: after its `X:` heading is stripped, `SQL Server: Stored procedures, queries, …`
   still lists generic nouns ("queries"), so it can flag a row that is fine. A review costs one
   `keep`.
4. **What stays with the analyst:** scope and intent lowerings, which no flag finds. The analyst
   still reads the evidence of every `satisfied` row, exactly as today. It now *writes* only the
   rows it lowers, not the whole table. *If wrong:* a later qualifier-word flag ("senior",
   "multi-", "executive" absent from the evidence) can be prototyped the same way. It is not in
   this plan, because the shown-but-not-named numbers suggest it would be noisy.
5. **The `gaps.txt` format mirrors `decisions.txt`.** Blank lines and lines starting with `#` are
   skipped. A keyed line matches `KEYED = (fit|eligibility|short|surplus|ask):[ \t]*(.*)`, as a
   fullmatch on the stripped line. It was run before planning: `short: gRPC | one service` is
   keyed, and `grpc | partial | one service` is a row.

   Every other line is a row, `slug | verdict | reason`, split on the first two `|`
   (`split("|", 2)`), so a reason may hold a `|`:
   - `slug` is the requirement's, as in `decisions.txt` (`req_<stem>_<slug>`). Rows pair by id,
     never by text.
   - `verdict` is a lowered verdict or `keep`, and `keep` is only valid on a flagged row.
   - `reason` is required with a lowered verdict and becomes `j:shortfall`.

   `fit` and `eligibility` appear at most once. `short`, `surplus` and `ask` may repeat; their
   order is their order in the file. If `ask` is present, the listed questions **replace** the
   derived ones. *If wrong:* a parser swap in one module.
6. **The draft `gaps.txt`** (`--draft-gaps`) holds only what needs judgement:
   - `fit:` pre-filled with the rule's default, which is a value, not a slot;
   - the person's eligibility facts and the advert's `elig` lines as `#` comments, then
     `eligibility:` with a slot;
   - one row per **flagged** requirement, `slug | <!-- jsk: keep, or lower: partial | unevidenced |
     unsatisfied --> |`, with its flag as a `#` comment above it;
   - `short:` with a slot, and `surplus:` with an optional slot;
   - the derived questions as `ask:` lines.

   Unflagged requirements are not listed. gaps.md shows them all with their evidence, and the
   analyst lowers one by adding a row. Any `<!-- jsk:` left in the file FAILs.
7. **The checks when the overlay is folded in** (`gapsbuild.check`). Everything `check_gaps`
   checks today is kept or made stronger. On any FAIL nothing is written.
   - FAIL: a row whose slug is not a requirement of the posting (today this only WARNs).
   - FAIL: a verdict above `j:matched`.
   - FAIL: a lowered verdict with no reason.
   - FAIL: `keep` on a row the flag did not fire on.
   - FAIL: a flagged row with no row in `gaps.txt`.
   - FAIL: an unfilled slot.
   - Evidence is derived, so it always exists. The cited-id check has nothing left to guard, and
     `cites_id` goes.
8. **`gaps.ttl` is re-derived on every run, then frozen at submission.**
   - `jsk tailor prepare` and `jsk match … --gaps` both rebuild it from the current career and
     `gaps.txt`, so there is no stale cache to warn about.
   - When the match has moved since the overlay was written:
     - the match now sits at or below a lowered verdict: WARN `the match now says X; the row
       lowers nothing - delete it`, and the lower of the two stands;
     - the match rose above a lowering: WARN `the match now says satisfied; you lowered it to
       partial because <reason> - still true?`.
   - Once `application.ttl` records `submitted` as a date, both commands refuse to rewrite
     `gaps.ttl`, because a sent assessment is what it said at the time.

   This is what makes the cross-application question answerable honestly: a sent application's
   `gaps.ttl` holds the verdicts from when it was sent. *If wrong:* the freeze is one check.
9. **The ids are derived, never chosen.**
   - The assessment is `k:gap_<stem>`, from `post_<stem>`.
   - A verdict is `k:vrd_<stem>_<slug>`, from `req_<stem>_<slug>`.
   - `gap` and `vrd` are unused prefixes (checked against `ontology.CLASSES`).

   A rebuild with no change is byte-identical.
10. **`gaps.ttl` is loaded with the workspace** (`store.load` globs it beside `posting.ttl`), so
    SHACL checks its refs and SPARQL can reach it. The refs are ordinary non-dangling `Ref`s. A
    dangling one FAILs in that application's directory. By `match.blocks` that stops only that
    posting, never another. *If wrong:* `may_dangle=True` on `evidence`.
11. **`jsk posting build --replace` deletes `gaps.ttl` and `gaps.md`, keeps `gaps.txt`, and says
    so.** A rebuild can drop a requirement `gaps.ttl` references, and that dangling ref would FAIL
    and block `prepare` in its own directory. `gaps.txt` is keyed by slug, so it survives any
    rebuild that keeps the slugs. A row for a slug that is gone FAILs under Ruling 7, and the
    message names it.
12. **Legacy `gaps.md` is not imported.**
    - `--gaps X.md` refuses: `gaps.md is written by jsk now; a gaps.md with no gaps.ttl beside it
      is an older assessment, read by people only`.
    - `gaps_table`, `cites_id` and `check_gaps` are deleted.

    *If wrong:* a one-off importer built from the deleted `gaps_table`.
13. **Out of scope:**
    - the kb auditor's `audit.gaps.md`, which is posting-less and a different shape;
    - a cross-application query noun, which would be new surface; Verification step 4 runs the
      query by hand;
    - kb.ttl `Question`s for posting questions: those belong to one run, not the career.
14. **Enums.** `verdict` is `satisfied, partial, unevidenced, unsatisfied, indeterminate`.
    `match.VERDICTS` and `RANK` become derived from `ENUMS["verdict"]`. `fit` is
    `strong, partial, poor`. `flag` is `listed-names`.

## Global constraints

- `jsk match`'s printed and `--json` output does not change.
- No new top-level verb and no new SKILL.md command row. `tests/test_plugin_surface.py` pins this.
- **Deriving must stay under 1 s** for one posting on the corpus, load included (measured today:
  about 600 ms). A test pins derive-only time on the largest fixture.
- Commit only the files a task names, never `git add -A`. Never commit while a subagent is working.
- Tests are unittest style, run with `python -m pytest tests -q -n auto`; lint with
  `python -m ruff check src tests`. After each task, run `pyright` on each changed module
  (`C:\Users\basil\.local\bin\pyright.exe`).
- Write any `.ttl` or regex-bearing file with the Write tool, never a heredoc (memory). Run every
  regex before trusting it.
- Re-measure the `tests/test_budget.py` ceilings for every prompt file that changes, and move them
  only with a measured comment.
- The flag's item splitting and matching, as executed before planning:

  ```python
  LIST_SPLIT = re.compile(r"\s*(?:,|/|\band\b|\bor\b)\s*", re.I)

  def listed(asked):
      """The items an `asked` lists, or None: `(a, b)`, or `a, b and c` itself."""
      asked = re.sub(r"\A[^():,]+:\s*", "", asked)          # a leading `X:` heading
      m = re.search(r"\(([^)]*)\)", asked)
      inner = m.group(1) if m else (asked if "," in asked else None)
      if inner is None:
          return None
      items = (x.strip(" .") for x in LIST_SPLIT.split(inner))
      return [x for x in items if x and x.lower() not in ("and", "or", "etc")]

  def present(term, texts):
      body = r"[\s-]+".join(re.escape(w) for w in re.split(r"[\s-]+", term.strip()) if w)
      return any(re.search(rf"(?<![A-Za-z0-9]){body}(?![A-Za-z0-9])", t, re.I) for t in texts)
  ```

  Results: `Vector databases (Pinecone, Weaviate, Milvus)` gives the three products.
  `Gemini, Cursor, and Claude` gives three items. `Kubernetes` and `CI/CD` give None.
  `present("Claude", ["Built with Claude Code"])` is True, and `present("Cursor", ["cursors"])` is
  False. The corpus rates in Ruling 3 were measured with a prefix-only `present`, without the
  trailing lookahead. Re-measure them with this version in Verification step 3.
